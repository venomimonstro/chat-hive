# CHAT Hive — финальный аудит ограниченного коммерческого выпуска

**Дата:** 17.10.2026  
**Ветка:** `main`  
**Первый выпуск:** CORE — личная текстовая переписка, регистрация, авторизация,
профиль, безопасность аккаунта и язык интерфейса.  
**Вердикт:** **NO-GO до завершения обязательной приёмки.** Исходный код
укреплён, но проверка в настоящей production-инфраструктуре не проводилась
в рамках этого аудита. Гарантий «100% защиты» не существует.

## 1. Подтверждённая реализация в исходном коде

| Контур | Что есть | Ограничение проверки |
|---|---|---|
| Состав продукта | Режим `CHAT_LAUNCH_MODE=core` включён по умолчанию; на сервере не регистрируются обработчики загрузок, групп, каналов, ленты, публикаций; независимый API allowlist возвращает 404 | Не подтверждён на фактически запущенной инсталляции |
| Аккаунты | Вход по одноразовой почтовой ссылке, Yandex ID, Passkeys, обновление и отзыв сессий; токен доступа только в памяти JS | Не проверена доставка SMTP/реальный Passkey на устройствах |
| Профиль | username, имя, необязательное описание; интересы больше не нужны | Нужны две реальные регистрации и повторные входы |
| Язык | `ru` по умолчанию, `en` доступен в настройках, хранится в PostgreSQL (`user_preferences`), применяется к основным экранам и синхронизируется при входе | Нужен полный визуальный просмотр RU/EN на экранах, в ошибках и на мобильных |
| Личная переписка | Только direct-чаты, сохранение сообщений, защита от повторной отправки через client_message_id, очередь офлайн-сообщений, WebSocket+REST восстановление | Не пройдены масштабная нагрузка/обрывы соединений/изоляция двух пользователей |
| Дизайн | Минималистичный интерфейс с отдельной колонкой чатов, областью сообщений и настройками, светлой базой, адаптивными стилями; аналогия с Telegram/ChatGPT по принципам, не копия | Визуальная и доступностная приёмка на реальных экранах ещё требуется |
| Приватность | Серверная проверка участия в чатах; закрыты публичные расширенные профили; приватный предварительный экспорт данных и ограничение параллельных экспортов | Независимое тестирование IDOR, BOLA, XSS, секретов, резервных копий не выполнено |
| Инфраструктура | HTTPS ingress через Caddy, HSTS, ограничение IP/частоты запросов, бэкапы, сценарии изолированного восстановления | Нет сведений о настроенном WAF/DDoS, внешнем offsite-хранилище и проделанном восстановлении |

## 2. Критические открытые блокеры

**P0-01. Воспроизводимая сборка.** В репозитории отсутствует настоящий
`web/package-lock.json`, тогда как Dockerfile применяет `npm ci`.
Следовательно, production-сборка фронтенда **не подтверждена и должна быть
заблокирована**. Создать lockfile на машине с доступом к реестру npm,
проверить `npm ci` и зафиксировать файл в отдельном коммите.

**P0-02. Полный quality gate.** Обязательны `gofmt`, `go vet ./...`,
`go test -race ./...`, чистые SQL-миграции, TypeScript `tsc --noEmit`,
`next build`, реальные `npm audit` и проверка версий контейнеров.
Последний проход изменений выполнялся через GitHub-коннектор без полноценного
Go1.24/npm окружения, поэтому **полный gate не был выполнен**. Исходный код
и наличие отдельных тестов не равны успешному тесту.

**P0-03. Эксплуатационная нагрузка.** Выполнить реальные HTTP, WebSocket,
reconnect-storm, логин, обмен сообщениями, offline/reconnect сценарии на
предпроизводственном экземпляре. Зафиксировать p50/p95/p99, ошибки, CPU,
RAM, disk I/O, размер очередей, лимиты соединений и план расширения
инфраструктуры. Целевые SLO согласовать заранее, а не подгонять под тест.

**P0-04. Информационная безопасность.** Независимый пентест с тестами
чужих сообщений/профилей, одноразовых ссылок, token replay, Passkeys,
WebSocket Origin, rate-limit bypass, XSS/CSP, CSRF, SQL-инъекций и
привилегий админки. Не открывать доступ при известных Critical/High.

**P0-05. Резервирование/восстановление.** Реально восстановить PostgreSQL
и медиа из проверенного зашифрованного offsite-архива в отдельной сети,
задокументировать RPO/RTO, частоту бэкапов, право доступа к ключам,
ротацию, срок хранения и сценарий потери VPS.

**P0-06. Юридическая и пользовательская приватность.** Определить
юрисдикцию, страну хранения, оператора ПДн, сроки хранения сообщений,
заявления в политике конфиденциальности, согласия, обработку запросов
на удаление/экспорт, правомерность сохранения сообщений после удаления
отправителя и порядок уведомления об инцидентах. Юрист должен утвердить
документы до получения платежей.

## 3. Остаточные риски и границы обещаний

- **Нет сквозного шифрования (E2EE)**: сервер обрабатывает сообщения в
  открытом виде. Нельзя рекламировать их как недоступные владельцу сервиса.
  TLS защищает передачу, шифрование дисков/бэкапов защищает хранение,
  но эти меры не заменяют E2EE.
- CSP фронтенда допускает `script-src 'unsafe-inline'`; устранение требует
  nonce/hash и регрессионного тестирования Next.js App Router. До этого
  внешний тест на XSS остаётся критическим блокером, а не пройденной мерой.
- Ограничитель запросов работает в памяти экземпляра; при нескольких API
  репликах нужна общая распределённая защита и ограничения на уровне
  ingress/WAF. DDoS-защита не доказана.
- Данные/таблицы будущих модулей сохраняются в общей схеме PostgreSQL.
  Закрытие функций в `core` не заменяет аудит миграций, привилегий БД и
  операций с историческими записями.
- Публичное отсутствие некоторых функций не означает отсутствие
  в коде всех модулей; их экспозиция сервером заблокирована и должна
  проверяться после каждого деплоя.

## 4. Обязательная приёмка пользовательских процессов

1. Регистрация из нового браузера, одноразовая ссылка, повторный вход,
   истёкшая/повторно использованная ссылка, потеря связи с SMTP.
2. Вход через двух независимых клиентов; смена/отзыв сессии, проверка
   доступности приватной переписки после выхода.
3. Создание username, смена имени, RU/EN из настроек и повторный вход
   на другом устройстве; язык по умолчанию RU.
4. Два разных пользователя: создать чат, отправить текст, получить через
   WebSocket, переподключиться, проверить REST-дозагрузку и сохранность.
5. Повторная отправка одного client_message_id не создаёт второй записи;
   отсутствие сети сохраняет сообщение в очереди. Отложенный ответ из
   предыдущего чата не меняет текущую переписку.
6. Пытающийся просмотреть историю третьего чата или изменить/удалить
   чужой текст получает 404 и не изменяет данные. Заблокированные
   контакты и непринятые запросы работают по утверждённой модели.
7. Прямые ссылки/API к изображениям, группам, каналам, ленте и
   публичным социальным профилям возвращают отказ.
8. Мобильный экран шириной 320–390 px: отсутствие горизонтального
   прокручивания, корректная экранная клавиатура, состояние пустого
   списка, фокус, контраст, скринридер, переключение RU/EN.
9. Экспорт/удаление аккаунта, возврат ошибки при недоступной БД,
   отсутствие неполного JSON при ошибке экспорта.
10. Проверить наблюдение ошибок, логирование без токенов/сообщений,
    понятное сообщение о техобслуживании и быстрый откат.

## 5. Протокол допуска к первому платному клиенту

1. `web/package-lock.json` создан настоящей установкой зависимостей и
   сохранён в Git. Выполнить `npm ci`, `npm audit`.
2. В отдельной среде выполнен `bash ops/release/check.sh` **без обходов**;
   приложены логи Go race, TypeScript, production build и миграций.
3. `CHAT_ENV=production`, `CHAT_LAUNCH_MODE=core`, реальные секреты и
   SMTP, корректный Caddy/TLS, приватные контейнеры БД.
4. Пройдены `ops/alpha/gate.sh` и двухпользовательский
   `ops/core/smoke.py` на **выделенных тестовых аккаунтах**.
5. Проведён независимый пентест с устранением всех High/Critical,
   подписаны юридические документы и фактическая аккредитация релиза.
6. Получен зашифрованный бэкап, проведено независимое восстановление,
   проверен мониторинг и откат.
7. `bash ops/core/gate.sh` завершён без ошибок и владелец сервиса
   зафиксировал ручную приёмку UX и рисков.

**Решение на дату аудита: запуск коммерческого трафика НЕ разрешён.**
Это предохранитель, а не оценка потенциала продукта. Протокол приёмки
будет изменён на GO только после появления проверяемых доказательств,
а не после очередного коммита.
