# CHAT Hive — UI/UX, производительность и adversarial security (CORE)

**Дата:** 17.10.2026
**Режим:** только регистрация, авторизация, аккаунт RU/EN, личные текстовые диалоги.
**Метод:** аудит исходников, моделирование нарушителя, изменение исходников напрямую
в `main` с регрессионными тестами и подготовкой ограниченного staging-пробника.
**Честный вердикт:** `NO-GO` для массовых платежей до запуска всех acceptance gates.

## 1. Клиентский UX: готовое поведение и негативные сценарии

| Экран/состояние | Принятая логика | Оставшаяся проверка |
|---|---|---|

| Регистрация/профиль | Имя, username, необязательная биография; без выбора интересов | Проверка коллизий username, нескольких вкладок, смены данных |
| Настройки | Русский по умолчанию, английский в профиле, сохранение на сервере; одинаковые словари основных экранов | Визуальный RU/EN-проход, длинные англоязычные подписи, скринридер |
| Список переписок | Отдельная область, поиск, «+» новый чат, пустое состояние, скелетон вместо скачка интерфейса | 320/360/390/768/1440 px, длинные имена, 100+ диалогов |
| Открытый чат | История из памяти вкладки появляется немедленно при повторном выборе; сервер всегда сверяется позже | Безопасность при смене аккаунта, история старше 40/24 сообщений |

| Медленный интернет | Скелетоны, очередь IndexedDB, фоновая досылка, 24 сообщения для 2G/экономии, серверная сверка после восстановления | Испытать 400 kbps/400ms RTT, offline/online, переключение вкладки |
| Безопасность аккаунта | Активные устройства, отзыв сессии, Passkeys, экспорт/удаление данных | Проверить реальное прекращение WebSocket и авторизации после отзыва |
| Функции следующих версий | Группы, каналы, изображения, реакции, лента, уведомления Push не открыты | E2E запросы напрямую к закрытым маршрутам |

## 2. Оптимизация без фиктивных обещаний о скорости

Реализовано в коде:

- Восьмипозиционный LRU-подобный кэш истории диалогов (только память вкладки);
  никакие приватные сообщения не сохраняются в CacheStorage/сервис-воркере.
- Черновики в памяти каждого диалога, возврат прокрутки при подгрузке истории,
  удержание последнего сообщения только когда пользователь читает конец.
- Одновременные проверки сессии объединены в singleflight с коротким TTL
  и мгновенной инвалидизацией при смене доступа. Получение RU/EN для аккаунта
  также не дублируется на каждой части страницы.
- Фоновая синхронизация настроена реже при работающем WebSocket; события
  «сообщение создано» объединяются в короткие пачки вместо каскада одинаковых запросов.
- Пустая очередь IndexedDB не вызывает сетевую проверку сессии.
- Размер страницы истории адаптируется: 24 записи для 2G/Data Saver,
  40 записей в обычном режиме, старая история загружается отдельно.
- Стили будущих модулей вынесены из глобального Next.js layout и
  загружаются при посещении соответствующих маршрутов.
- Сервис-воркер первой версии кэширует только публичные статические файлы,
  не хранит HTML/API и не регистрирует будущие push-уведомления.

**Целевые, ещё НЕ измеренные показатели (предложение для испытаний):**
локальная реакция поля ввода p95 менее 100 мс; на обычной мобильной сети
p95 подтверждения отправки менее 1,5 с; на испытательном 3G профиле LCP
не более 4 с; плавное прокручивание 50 пузырьков сообщений; 0 потерь
данных очереди в 100 циклах offline/reconnect. Зафиксировать фактические
TTFB, LCP, INP, CLS, p95/p99 API, размер начальных JS/CSS чанков, число
запросов, CPU/RAM сервера, время переключения диалога и долю неудачных
сообщений. Это **не результаты измерений**.

## 3. Моделирование нарушителя (без нападения на чужую инфраструктуру)

| Проверка/угроза | Что сделано | Остаток |
|---|---|---|
| Поддельный Bearer и гость → чужая переписка | Дополнен безопасный staging `ops/core/security_probe.py` | Запустить на собственном staging с двумя тестовыми аккаунтами |
| Подмена chat/message UUID, удаление чужого текста | Негативные E2E сценарии в `ops/core/smoke.py`; объектные проверки на сервере | Протестировать на реальной PostgreSQL с отрицательными правами |
| Cross-site WebSocket | Точное совпадение HTTPS Origin, отказ при пустом Origin до потребления билета | Проверить WSS за реальным Caddy/CDN и при ошибке прокси |
| Отозванный аккаунт / смена пользователя в той же вкладке | Очистка локальной истории и закрытие старого WebSocket | Серверный WS принудительно ограничен 5 мин, но для мгновенного отзыва нужна отдельная доставка события ревокации |
| Аварийно отключённая функция при ошибке БД | Kill-switch fail-closed (503), не «разрешить при ошибке» | Проверить аварийную команду на рабочей схеме feature flags |
| Новые API функций будущих выпусков | По умолчанию режим core; лишние роуты не регистрируются и отсекаются allowlist | Контроль после каждого деплоя |
| Раскрытие приватного HTML через PWA-кэш | HTML, API и навигация не кешируются; push удалён из core воркера | Проверить обновление SW на устройствах старых пользователей |
| DoS через экспорт аккаунта | 2 параллельных экспорта, ограниченный объём временных файлов, атомарная подготовка ответа | Мониторинг /tmp, дисковой квоты, максимальных экспортов и очереди |
| Парсинг HTTP JSON | Неожиданные поля и несколько JSON-значений отклоняются | Pentest unicode/UTF8/boundaries в пределах безопасных rate limits |

## 4. Критические блокеры коммерческого запуска (P0)

1. **Нет настоящего `web/package-lock.json`.** Поэтому не подтверждена
   воспроизводимая Next.js production-сборка. Нельзя пропускать `npm ci`.
2. **Не выполнены полноценные тесты Go 1.24 и Next 15.** В рамках редактирования
   GitHub-коннектором выполнены проверки наличия исходников и синтаксиса JS
   регрессионных файлов; `go test -race`, `gofmt`, `tsc`, полноценный
   `next build` и Docker-интеграция требуют окружения с зависимостями.
3. **CSP всё ещё разрешает `script-src 'unsafe-inline'`.** Перед открытием
   доступа нужна проверка XSS и переход на подходящую nonce/hash-политику,
   совместимую с текущей версией Next. Нельзя считать XSS исключённым.
4. **Не проведены измерения 2G/3G, мобильного UX и доступности.** Нужны
   объективные замеры до и после оптимизаций, реальные устройства.
5. **Нет подтверждения независимого пентеста, WAF/DDoS-политики,**
   шифрования/восстановления реальных offsite backup, RPO/RTO, процедуры
   ротации ключей и эксплуатационной готовности.
6. **WebSocket ревокация пока не мгновенная на сервере.** Введён предел
   соединения 5 мин и клиентская очистка при изменении сессии, но
   требуется серверный сигнал немедленного прекращения после блокировки
   пользователя или отзыва сессии.
7. **Нет E2EE.** TLS и доступ по ролям ≠ сквозное шифрование. Не делать
   соответствующих заявлений в маркетинге.

## 5. Приёмка

При наличии Go 1.24+, npm/Node и изолированного тестового сервера:

```bash
bash ops/release/prepare-lockfile.sh
# Зафиксировать настоящий web/package-lock.json отдельным коммитом
bash ops/release/check.sh

# Только собственный staging с двумя выделенными тестовыми аккаунтами:
export CHAT_CORE_ATTACK_SIMULATION_ACK=I_OWN_THIS_STAGING_HOST_AND_APPROVE_SAFE_TESTS
# Остальные переменные из docs/CORE_COMMERCIAL_LAUNCH.md
python3 ops/core/smoke.py
python3 ops/core/security_probe.py
```

Выполнить мобильную визуальную приёмку, независимый пентест, измерение
p95/p99 и восстановление из offsite архива. Финальный
`bash ops/core/gate.sh` не имеет права пропускать хотя бы один этап.

**Итог: source-level усиление завершено в рамках текущего прохода,
но эксплуатационный статус по-прежнему NO-GO, не «идеально» и не «100% безопасно».**
