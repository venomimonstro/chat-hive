# CHAT — Closed Alpha Runbook

Closed Alpha is a controlled production-like deployment for a limited invited cohort. It is not a substitute for the Public Beta security/legal gate.

## 1. Entry criteria

Do not deploy Alpha until all conditions below are satisfied:

1. `web/package-lock.json` was generated by npm and committed; it was not hand-written.
2. `ops/release/check.sh` passes on the deployment environment.
3. All migrations apply from zero to an empty PostgreSQL database.
4. A database + media backup is created and a restore drill succeeds on a separate target.
5. Load harness establishes a safe concurrency limit for the actual server.
6. Production SMTP is verified with a controlled test account.
7. Yandex OAuth callback is HTTPS and verified if Yandex login is enabled.
8. No known exploitable Critical/High issue remains.
9. Admin/security roles are provisioned to named operational accounts only.
10. Legal/compliance production qualification is tracked separately; Closed Alpha does not waive it.

## 2. Production network contract

Public ingress may reach only:

- HTTPS reverse proxy / web frontend;
- HTTPS API and WebSocket paths through the same trusted edge.

The following services must not have public listeners:

- PostgreSQL;
- Redis;
- NATS;
- internal media filesystem/object-storage management endpoint;
- backup storage;
- admin database tooling.

Do not trust arbitrary `X-Forwarded-For`. If a reverse proxy is introduced, trusted-proxy handling must be explicitly implemented and scoped to the proxy network before forwarded addresses are used for security decisions.

## 3. Required production variables

Secrets are supplied outside Git.

Required baseline:

```text
CHAT_ENV=production
CHAT_DATABASE_URL=postgres://<non-default-user>:<secret>@<private-host>:5432/<db>?sslmode=<required-mode>
CHAT_WEB_ORIGIN=https://<public-web-host>
CHAT_MAGIC_LINK_BASE_URL=https://<public-web-host>/auth/callback
CHAT_SMTP_ADDR=<smtp-host:port>
CHAT_SMTP_USERNAME=<if required>
CHAT_SMTP_PASSWORD=<secret>
CHAT_SMTP_FROM=<verified sender>
CHAT_MEDIA_ROOT=<persistent alpha media path>
NEXT_PUBLIC_API_BASE_URL=https://<public-api-host>
CHAT_INTERNAL_API_BASE_URL=http://<private-api-service>:8080
```

Optional:

```text
CHAT_YANDEX_CLIENT_ID=<client id>
CHAT_YANDEX_REDIRECT_URL=https://<public-api-host>/api/v1/auth/yandex/callback
NEXT_PUBLIC_VAPID_PUBLIC_KEY=<only after vetted Web Push sender is enabled>
```

## 4. Deployment order

1. Freeze the release commit SHA.
2. Record migration version and release owner.
3. Create pre-deploy database/media backup and record checksums.
4. Run `ops/release/check.sh`.
5. Apply migrations with a dedicated migration credential, not the normal application credential where practical.
6. Start PostgreSQL/Redis/NATS private infrastructure.
7. Start API.
8. Verify `/health/live` and `/health/ready` through internal and public edge paths.
9. Start web frontend.
10. Execute smoke tests in section 5.
11. Open access only to the Alpha invite cohort.
12. Monitor HTTP errors, realtime disconnects/drops, security events and DB resource usage during the first hour.

## 5. Mandatory smoke test

Use dedicated test accounts; never production administrator credentials for ordinary smoke scenarios.

### Identity

- Email magic link creates/opens a session.
- Refresh rotation works.
- Session appears in Security Center.
- Session revoke terminates that device.
- Yandex login works if enabled.

### Social

- Finish onboarding.
- Open public profile anonymously.
- Follow after login.
- External profile link returns user to the profile after login/onboarding.

### Messaging

- Create direct chat.
- Stranger request permits only the initial request until accepted.
- Accept request and continue same chat ID.
- Send a message online.
- Send while offline, reload browser, restore network and verify exactly one delivered message.
- Reply/edit/delete own message.
- Add/remove reaction.
- Confirm acknowledged messages remain available when WebSocket is interrupted and REST recovery runs.

### Groups

- Create group.
- Create/join invite.
- Promote admin.
- Admin can moderate a message only in that group.
- Transfer ownership then leave previous owner.

### Public content

- Create thought/photo/post.
- Public permalink opens without authentication.
- Public media loads anonymously only through public post linkage.
- Follower-only content is not readable anonymously.
- Approved community/channel opens without login.
- Pending/private community/channel does not enter the guest path.

### Moderation / security

- Submit report.
- Case appears in moderation queue.
- Resolve/dismiss case with an authorised admin.
- Audit record is created.
- Trigger a controlled rate limit and verify aggregated security event.
- Security/owner can view `/admin/security`; ordinary admin roles cannot.

## 6. Load validation before invites

Run the repository load harness against the actual Alpha host and record:

- hardware/server plan;
- HTTP RPS;
- p50/p95/p99;
- error rate;
- concurrent WebSocket connection count;
- realtime `published/dropped` counters;
- CPU/RAM/DB connections;
- reconnect-storm behavior.

Set the initial invite cap **below** the measured safe ceiling with a substantial reserve. Do not infer capacity from local benchmarks.

## 7. Monitoring during Alpha

At minimum monitor:

- API 5xx rate;
- auth 401/429 spikes;
- PostgreSQL CPU/RAM/storage/connections;
- disk/media growth;
- realtime connections/published/dropped;
- backup success;
- `critical/high` security events;
- moderation queue age;
- message send error rate;
- signup → onboarding completion;
- first message / first follow / first post;
- D1/D7 retention once enough cohort data exists.

## 8. Controlled degradation

When infrastructure is stressed, preserve in this order:

1. Messaging and REST recovery.
2. Authentication.
3. Profiles.
4. Feed.
5. Discovery/analytics.

Feed/Discovery may be throttled before messaging. Do not disable durability/idempotency/security checks to gain throughput.

## 9. Rollback

Rollback only to a commit compatible with the current schema.

1. Stop new writes if a destructive rollback is required.
2. Preserve logs/security evidence.
3. Decide whether application rollback alone is sufficient.
4. Never run down-migrations blindly on production data.
5. For data corruption, restore into an isolated target first and verify before replacing production.
6. After rollback, re-run health and smoke tests.

## 10. Alpha cohort strategy

Start with a small set of dense communities rather than random registrations:

- gaming;
- university/friend groups;
- small creators;
- hobby communities.

Use invite waves. Increase the cohort only after reliability, moderation workload and resource consumption remain within defined thresholds.

## 11. Exit criteria to Sprint 29

Closed Alpha produces measured evidence, not opinions. Record:

- activation funnel;
- D1/D7;
- conversations/user;
- accepted stranger requests vs spam/rejects;
- new follows/connections;
- creator exploration → profile/follow conversion;
- invite conversion;
- moderation false positives/queue time;
- reliability and capacity data.

Sprint 29 prioritizes only defects/opportunities materially affecting activation, retention, network growth, trust, stability or cost.
